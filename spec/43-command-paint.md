# Opaque command paint (candidate, schema 0.2.0)

This contract resolves the body and independent navigation paint of an ordinary command surface. It builds on [state composition](16-state-composition.md), [opaque surface appearance](36-opaque-surface-ir.md), the [lit control body](88-lit-control-body.md) and the focus member of [complete surface paint](39-surface-paint-ir.md). The operation is headless and renderer agnostic. It defines static endpoints; it does not define a transition trajectory or a complete Button component.

## Scope and state channels

A request MUST use a `control.passive`, `control.interactive`, or `control.primary` material role, bound through the actual theme and environment. Cast, Frost and Elastomer are valid command families. Gel MUST NOT be used. Supported signals are `rest`, `hover`, `pressed`, `disabled`, and `focused`, in any valid nonempty combination. Every other signal MUST fail explicitly until its component appearance contract exists.

The body phase is `disabled` when disabled is present, otherwise `pressed` when pressed is present, otherwise `hover` when hover is present, otherwise `rest`. This is precedence for this command body's pigment and depth channels, not a change to the state set or a general state precedence rule. All input signals MUST remain in the body IR and any navigation binding. `focused` independently requires a visible focus indicator, including when pressed or disabled is also present. State selection MUST NOT infer enablement, focus eligibility, activation, selection, or a semantic action. The [activation contract](42-command-activation.md) owns gesture lifecycle.

## Authored responses

The appearance document, its material-family collection, each family's phase collection, and every response MUST be JSON objects with named members. Positional arrays are invalid. The [appearance schema](../schemas/command-appearance.schema.json) requires explicit hover, pressed and disabled responses for each of Cast, Frost and Elastomer. Every profile MUST be structurally validated, including families and phases not selected by this request. Perceivability is measured on a body, so resolution checks it only for the bound family on the body being resolved, as described below. There are no backend defaults. Rest is the identity response: `bodyMix = 0` and `depthScale = 1`.

`bodyMix` MUST be finite and in [-1, 1]. For an encoded sRGB body channel `c`, a negative mix `m` resolves to `c * (1 + m)`; a nonnegative mix resolves to `c + (1 - c) * m`. Alpha is preserved. This uses the same encoded sRGB shade/lift convention as the existing opaque pigment contract. The response applies to both the opaque fallback body and Frost's actual portable body before legibility selection. Semantic color role remains unchanged, and the foreground remains unchanged except for the [disabled label](#disabled-label). Final content contrast MUST be calculated against the actual resolved body, never the unmodified rest body. Insufficient contrast MUST fail; the operation MUST NOT silently reduce the authored response.

`depthScale` MUST be finite and in [0, 2]. Final depth is the theme-bound semantic elevation depth multiplied by this scale. The front contour and content footprint remain stable; only the dimensional extrusion changes. A scale below 1 compresses the extrusion and a scale above 1 raises it. This is a depth change, not in-plane elastic deformation. Body silhouette, edge interior and focus silhouette MUST all use this same final depth. The semantic elevation remains available as intent in the IR.

### Perceivable state responses

Each authored hover, pressed and disabled response of the bound family MUST be perceivable from rest through at least one measurable channel:

- **body color:** the Euclidean Oklab difference ΔE_OK between the resolved opaque body with the response applied and the same bound opaque body at rest is at least 0.04; or
- **depth:** the final extrusion depth differs from the rest depth (the semantic elevation depth) by at least 1 logical `px`. Compare with an absolute geometric tolerance of `1e-12` logical `px`, as in [focus geometry](37-focus-indicator-ir.md).

The disabled response MUST also be perceivable from the pressed response through the same two channels, measured between the two responded bodies: ΔE_OK between the pressed and disabled bodies, or the difference of their final depths, with the same thresholds and tolerance. Disabled and pressed both compress the body, and the body itself must tell them apart: the disabled label cue is not available on every body, because Toggle parts carry no label and a label already at its disabled bound cannot dim further. On a raised body of 2 px semantic depth, two compressions that each differ from rest and from each other by 1 px leave exactly one arrangement: one of them flat and the other 1 px deep.

Measure on the opaque body the response is applied to, using the [Oklab conversion](04-color-conversion.md) of its encoded sRGB channels. For Frost this is its opaque fallback body, because this operation only publishes an `opaqueDimensional` representation. Rest is the identity response and is not measured. An embedded body with zero semantic depth can only satisfy the color channel. Resolving any state, including rest, validates all three responses of the bound family and the disabled-from-pressed pair on the body being resolved, so an imperceptible profile fails at its first resolution rather than at the first hover or disablement. When a response satisfies neither channel, resolution MUST fail with a diagnostic naming its phase and publish no partial IR. The operation MUST NOT strengthen, replace or omit an authored response to pass. Only authored responses are measured; sampled motion responses between endpoints are not.

The 0.04 threshold is twice the commonly cited informal ΔE_OK just-noticeable difference of about 0.02. That figure is not a standard and depends on the display; the factor of two leaves margin for display variation. The 1 `px` depth threshold is one logical pixel of physical extrusion change. Both channels keep the semantic color role unchanged, so existing content and edge contrast guarantees remain; only the disabled label below changes the foreground. On near-white light-theme bodies a lift cannot reach the color threshold; such responses darken or rely on depth.

The [light](../definitions/command-appearance-light.json) and [dark](../definitions/command-appearance-dark.json) definitions are reference authoring, not universal numeric material constants. Hover raises the body, pressed compresses it by 1 px and disabled flattens it completely, the only arrangement on a 2 px raised body that keeps disabled 1 px from both rest and pressed. Cast keeps the most restrained rise and color mix and Elastomer the strongest, following the blueprint's qualitative family distinction; the pressed depth no longer differs by family. Every family's body mix stays within the range that keeps an embedded Toggle track perceivable, its thumb edge guard satisfied and its pressed and disabled colors at least ΔE_OK 0.04 apart in each theme. A reference test measures the shipped definitions in both themes under every family a theme may assign to each control role, for both Command bodies and both Toggle parts. These values do not calibrate spring mechanics or promise physical simulation. Products and themes may supply different validated responses that satisfy perceivability, contrast and material identity requirements.

### Disabled label

The disabled phase also dims the label. After the content guard has selected a foreground against the disabled body, mix that foreground toward the resolved body in linear-light sRGB by the largest fraction whose [contrast](12-contrast.md) against the body is not below the disabled bound `B`: **3:1**, or **4.5:1** when the actual environment's high-contrast preference is set. Relative luminance is linear in that mix, so the fraction has a closed form: for a darker foreground the target luminance is `(Lbody + 0.05) / B − 0.05`, for a lighter one `B (Lbody + 0.05) − 0.05`. A foreground at or below `B`, or within `1e-9` above it, stays unchanged, and so does one whose rounded mix cannot reach the bound from above. Encode the mixed color and publish it with its actual ratio, which is `B` to within `1e-9` above; never below. The bound applies to the published color. A renderer that quantizes it, for example to 8-bit channels, can measure slightly below `B`. Hover, pressed and rest keep the guarded foreground. The dimmed color and its ratio replace exactly `face.foreground` and `face.contentContrastRatio` of the lit body; every other member and every sampled color is the undimmed body. The content guard with the request's minimum still applies first, so the dimmed label is always derived from a legible foreground; the bound then replaces that minimum for the disabled state only.

The bound is chosen from these references:

- [WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) exempts "text or images of text that are part of an inactive user interface component" from its minimum, so dimming does not breach it. The same criterion uses 3:1 as the minimum for large-scale text, and [SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) uses 3:1 for user interface components.
- Material 3 draws disabled label text in `onSurface` at 0.38 opacity over a 0.12 `onSurface` container (`md.comp.filled-button.disabled.label-text.opacity`, in the [generated token data](https://flutter.googlesource.com/mirrors/flutter/+/a7f8b31beb4816d24cf993fdd916d97e75fabf56/dev/tools/gen_defaults/data/button_filled.json)). For the [baseline scheme](https://m3.material.io/styles/color/static/baseline), onSurface `#1D1B20` on surface `#FEF7FF` and `#E6E0E9` on `#141218`, that gives about 2.3:1 in light and 2.9:1 in dark, so the label is unbounded below 3:1.
- Apple's [color guidance](https://developer.apple.com/design/human-interface-guidelines/color) provides a dedicated "unavailable control text" system color for the text of a control that is unavailable, without a published ratio.

3:1 keeps a disabled label legible at the WCAG large-text and component threshold, unlike the Material 3 opacity rule, while the enabled guard of at least 4.5:1 makes every dimmed label at least 1.5 times lower in contrast than its enabled state. Under the high-contrast preference the label still dims, but only to 4.5:1, the WCAG 2.2 AA text minimum, as high-contrast platform themes keep a dedicated, still legible disabled text color; a label already at or below 4.5:1 there keeps its guarded color.

## Resolution and fallback

Resolve the actual environment and theme once. Bind the original surface and preserve its full state set. Validate that every authored response of the bound family is perceivable from rest, apply the selected authored body response, then run the existing content and adjacent-edge guards, resolve the lit control body and, in the disabled phase, dim the label. Frost MUST retain actual capability, preference and legibility selection. An opaque output is valid only when the resulting Frost representation is genuinely `opaqueDimensional`; a remaining translucent representation MUST fail this opaque operation. Do not force reduced transparency or change capability flags to obtain a desired output.

Resolve shape, final depth, key light, family pigment, the body relief and its light using the existing portable laws and the lit control body. If focused, resolve the independent focus contrast and ring against the same response geometry. Focus remains geometrically separated from the body. The operation MUST publish the complete result atomically: any body, geometry or navigation failure produces no partial IR. Static endpoints remain usable with reduced motion; no animation is introduced by this operation. Text scale and locale remain in the actual environment and do not implicitly shrink the authored body or hit region.

## Light and relief

The body is the [lit control body](88-lit-control-body.md) of the responded body color at the final depth. Its outline F uses the bound Tier 0 shape fallback of the command size with `circular` curvature, the actual layout direction and the family's exterior `edgeWidth` as minimum inset; the family's `highlightWidth` is not used. The appearance `keyLight` resolves both the side offset and the face light.

The request carries two required members:

- `light`, the unversioned light channels object with exactly `ambient` and `interaction`. Absence of either channel is explicit null. Validate the original source coefficients of every supplied channel under the [bounded material-light source rule](85-bounded-material-light.md#inputs-and-fallback), including channels the policy or the phase suppresses: a negative nonzero ambient or interaction strength is invalid even when binary64 decoding would erase it to negative zero.
- `relief`, a complete [control relief](../schemas/control-relief.schema.json) document. Every part profile is validated; the command body uses `commandBody`. Neither state, material family nor depth scale selects or scales the relief. A rounded corner that cannot carry the shoulder fails with the lit-body diagnostic prefixed by `commandBody`.

The interaction channel is admitted exactly when the body phase is `hover` or `pressed`, then follows the bounded material-light environment policy unchanged. `focused` alone and `disabled` never admit it. A keyboard press reaches the pressed phase; a product without a pointer direction supplies null interaction and no directional light appears. Light never changes the body, edge or foreground and is never a state cue: perceivable state responses and contrast are measured on the unlit body and the final depth exactly as above, so suppressing light never removes a cue. The resolved body uses no gradient, mask, shader or dynamic primitive, so only the documented interaction suppression responds to capabilities.

## Wire contract and conformance

The [request](../schemas/command-paint-request.schema.json), version 0.2.0, wraps a complete surface request, explicit command appearance, light channels and control relief. The request MUST be a JSON object; positional request records are invalid, and version 0.1.0 requests are rejected. The [result](../schemas/command-paint-ir.schema.json), version 0.2.0, contains `phase`, `response`, and complete `paint`, the [lit control paint](../schemas/lit-control-paint-ir.schema.json) with the command state domain. Consumers tell this body apart from the spec/36 body by these envelopes. The superseded 0.1.0 [request](../schemas/versions/command-paint-request-0.1.0.schema.json), [result](../schemas/versions/command-paint-ir-0.1.0.schema.json) and [body](../schemas/versions/command-body-ir-0.1.0.schema.json) schemas remain archived. The existing base-state surface operation and its schema remain restricted to rest/focused.

The Rust reference exposes typed and strict source operations; `resina-command-paint <path|->` reads one UTF-8 request, with a 1 MiB limit, writes one result on success, exits 1 with a diagnostic and no output on failure, and exits 2 for invalid usage. Duplicate and unknown JSON members MUST fail. [Public cases](../conformance/ir/command-paint-cases.json) and the independent backend checker cover precedence, state preservation, authored response arithmetic, perceivable state responses, contrast, matching focus geometry and strict failure paths. They also cover every phase with light admitted and suppressed, including a keyboard press without interaction, every environment condition of the policy, explicit and absent channels, negative-zero coefficient sources in suppressed channels and invalid relief. The checker derives the expected light, pigment, edge, content rectangle and lit-body invariants with [independent arithmetic](../tools/lit_body_arithmetic.py), and repeats every state set of every family in an admitting environment with and without light, requiring identical output apart from `face.light`. The CPU and GUIdo paint consumers accept the resolved complete paint directly; they do not implement command state or light rules. The [lit body raster checker](../tools/check_lit_body_raster_backend.py) compares every pixel of the CPU raster with the independent arithmetic.

A complete command component still owns anatomy, label layout, semantics, accessibility exposure, native event routing, localization, target placement and motion. This paint contract does not claim those responsibilities are implemented.

Failure diagnostics follow the [public backend diagnostic policy](32-headless-conformance.md#failure-diagnostics). Negative public cases use `failure: true`; diagnostic wording is not a conformance requirement.
