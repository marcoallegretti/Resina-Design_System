# Token format and authority (candidate)

Generic Resina design tokens MUST use the [DTCG Design Tokens Format Module 2025.10](https://www.designtokens.org/TR/2025.10/format/). Color tokens MUST follow its [Color Module 2025.10](https://www.designtokens.org/TR/2025.10/color/). These are stable Design Tokens Community Group reports, though they are not W3C Standards. Resina does not define alternate syntax for token values, groups, type inheritance, aliases, or group extensions.

Authoring files in `tokens/` are normative. Generated Rust constants, backend assets, and compiled bundles are derived artifacts. A backend MUST NOT infer token meaning from a group name or a physical color value. It MUST consume the resolved token type and the semantic role specified by Resina.

JSON authoring sources MUST reject duplicate object member names at every depth before conversion to a value tree, including names that decode to the same string through JSON escapes. A last-member-wins parse can change token meaning before structural or reference validation sees it. The [source vectors](../conformance/tokens/source-vectors.json) define parsing outcomes and duplicate-member locations. Source parsing establishes only unambiguous JSON; document resolution and value validation remain separate gates.

A source-to-token operation MUST run that duplicate-safe parse before document resolution and MUST stop on a parse error. It MUST NOT publish a partial token mapping when document resolution finds an error. Parse and resolution failures remain distinguishable. The [source pipeline vectors](../conformance/tokens/source-pipeline-vectors.json) cover the complete operation. The Rust reference exposes it as `resolve_token_source`; callers supplying an already parsed value to the lower-level document resolver are responsible for preserving the source gate when processing authoring files.

Resina organizes authoring tokens into foundation, semantic, and occasional component layers. Foundation tokens contain raw scales. Semantic tokens name intent and SHOULD alias foundation or other semantic tokens. Component tokens SHOULD exist only when a semantic token cannot express the needed component contract. Alias cycles, unresolved references, missing types, and invalid values MUST be rejected. Implementations processing the format MUST support both whole-token curly-brace aliases and JSON Pointer `$ref` references, including chained references and cycle detection, as required by the DTCG format.

A curly alias implicitly selects its target token's `$value`; the target MUST contain `$value`. A JSON Pointer selects its literal document location: a token value alias MUST include `/$value` (for example, `"$ref": "#/base/$value"`). A pointer ending at the token object (for example, `"$ref": "#/base"`) resolves to that object and is subject to the receiving token's value-shape validation.

Group extensions and token-set composition are processed before a token's aliases are resolved. Reference resolution does not itself validate the resolved value's declared type; type validation MUST follow before a token enters a Resina bundle. The [reference vectors](../conformance/tokens/reference-vectors.json) cover whole-token aliases, property references, escaped JSON Pointers, cycles, and invalid targets.

For `$extends`, a local token definition replaces the complete inherited token at the same path. Local and inherited groups merge recursively; local group metadata replaces inherited metadata at the same property. Extension targets MUST be groups, and inheritance cycles are invalid. The [extension vectors](../conformance/tokens/extension-vectors.json) define these outcomes and errors.

Extension graphs and reference graphs can expand a compact authoring source into a much larger document or resolved value. An implementation MAY impose documented resource bounds on this work. Exceeding a bound MUST produce an explicit diagnostic without a partial token mapping. Bounds are implementation-specific, not DTCG semantic limits or cross-backend conformance values.

The [structure vectors](../conformance/tokens/structure-vectors.json) cover group and token shape, metadata, reserved names, and root tokens. Structural validation alone does not establish DTCG conformance: extension targets, inherited types, and each declared value type also require validation.

After group extensions are materialized, a token's explicit `$type` takes precedence. Without one, a whole-token alias inherits its target token's resolved type; otherwise the closest ancestor group's `$type` applies. A JSON Pointer to a token property does not establish that property's type and needs an explicit or inherited declaration. Resolvers MUST NOT infer types from values. The [type vectors](../conformance/tokens/type-vectors.json) cover these cases, missing types, and alias cycles. Value-shape validation remains a separate required gate.

The [primitive value vectors](../conformance/tokens/primitive-value-vectors.json) cover resolved `number`, `dimension`, `duration`, `fontFamily`, `fontWeight`, `cubicBezier`, and `color` values. The [color-space vectors](../conformance/tokens/color-space-vectors.json) exercise every 2025.10 color space and representative component boundaries. Validation follows the DTCG Format and Color modules, including units, color spaces and component ranges, alpha, hex fallbacks, and Bézier control points.

A `fontFamily` string or each member of a fallback list MUST name a font; an empty or whitespace-only name is invalid. The validator does not infer whether a nonempty name is installed on a device.

The [fixed composite vectors](../conformance/tokens/fixed-composite-vectors.json) cover resolved `strokeStyle`, `border`, `transition`, and `typography` values, including each named sub-value's required type. The [array composite vectors](../conformance/tokens/array-composite-vectors.json) cover resolved `shadow` and `gradient` values, including nested arrays preserved by references. A resolved value alone cannot distinguish a referenced nested array from an explicit nested array in the authoring file; authoring-reference validation MUST make that distinction before bundle compilation. The DTCG Format prose requires out-of-range gradient stop positions to be clamped by consumers, even though its published JSON schema limits them to `[0, 1]`; Resina follows the prose and preserves the numeric source value during validation.

The [document vectors](../conformance/tokens/document-vectors.json) define headless resolution of a complete authoring document. Group extensions are materialized once, every token receives a declared type, whole-token references MUST match the expected type at their use site, and every resolved value is validated. Output is a deterministic path-to-token mapping. This mapping is a token resolution result, not a Resina bundle: theme, material, adaptation, accessibility, and fallback semantics require separate Resina contracts.

The [source pipeline vectors](../conformance/tokens/source-pipeline-vectors.json) and document vectors can be checked through a language-neutral command boundary with `python tools/check_token_backend.py -- <backend-command> -`. The command MUST read one UTF-8 DTCG JSON source from standard input. On success it MUST exit 0, emit exactly one JSON object mapping token paths to objects with `token_type` and `value`, and leave standard error empty. On failure it MUST exit 1, emit no standard output, and provide a nonempty diagnostic on standard error; diagnostic wording is implementation-specific. Valid sources are invoked twice in fresh processes to check deterministic output. The checker compares resolved values exactly, with JSON numeric equality, and rejects duplicate members and nonfinite numbers in backend output. It establishes conformance only for the covered token-source and document-resolution cases, not bundle or IR conformance.

A group's `$root` token has an explicit path ending in `.$root`; the group path alone does not refer to that token. Root tokens inherit the group's declared type when they have no explicit `$type`. The document vectors cover both the valid root-token alias and invalid group alias.

The DTCG value schemas restrict several scalar sub-values, including dimension units and color components, to JSON Pointer property references. Curly aliases in those positions are invalid even if they would resolve to a compatible JSON value. A custom stroke style MUST have at least one dash-array entry.

The [DTCG Resolver Module 2025.10](https://www.designtokens.org/TR/2025.10/resolver/) is also a stable Community Group report. Its token-set and modifier composition belongs to authoring, before DTCG token aliases and Resina semantic bindings. It does not define Resina's resolution of material roles, environment, component state, accessibility, renderer capabilities, quality policy, or fallbacks into Resina IR. The Resina resolver MUST define those decisions independently.

The Rust reference's `resolve_resolver_module_source` accepts one resolver JSON source, one JSON input object, and an explicit URI-to-source-text map. It supports inline and same-document references, and external DTCG token documents supplied by that map; it does not fetch files or URLs or import external resolver definitions with nested relative links. Missing referenced sources fail diagnostically. Input names and context values are case-sensitive, as permitted by the Resolver Module. The operation composes sets and selected modifier contexts in `resolutionOrder`, replaces a conflicting token as a whole, resolves aliases only after composition, and publishes no partial mapping if the final DTCG token document fails validation. Unselected external context documents are not parsed. The [resolver-module vectors](../conformance/tokens/resolver-module-vectors.json) and their [case schema](../schemas/resolver-module-case.schema.json) exercise ordering, selection, reference overrides, and failures; a reference test composes the actual authored foundation source. A [theme source](22-theme-compilation.md) can consume this result for semantic binding. The reference bounds supplied source bytes and composition work by nodes and copied text bytes; exceeding a bound fails without output.

The [resolver request](../schemas/resolver-module-request.schema.json) is a versioned command envelope containing the resolver JSON text, input JSON text, and explicit URI-to-text source map. The `resina-token-compose <path|->` command MUST read one UTF-8 request from a file or standard input. On success it MUST exit 0, write exactly one deterministic JSON object mapping token paths to `token_type` and `value`, and leave standard error empty. On invalid input or failed composition it MUST exit 1, write no standard output, and provide a nonempty diagnostic on standard error. Usage errors exit 2. The Rust command bounds input bytes before parsing. The [external backend checker](../tools/check_resolver_backend.py) runs every resolver vector, composes the actual authored foundation source, and checks strict output, deterministic repetition, diagnostics, and absence of partial output through this language-neutral boundary. Passing it establishes conformance only for covered token composition behavior, not theme, bundle, or IR resolution.

The calibrated candidate spatial scale is defined by the [spatial contract](10-spatial.md) and its DTCG source. This token-format document does not fix a palette; color assignment still requires legibility and fallback contracts. Values MUST NOT be presented as normative before their contracts and conformance cases exist.
