# Theme source compilation (candidate, 0.1.0)

A [theme source](../schemas/theme-source.schema.json) groups material, Frost pigment, color, opaque color, spatial, and typography assignments for one selected theme with exactly one token authoring form: an embedded DTCG `tokens` document, or a DTCG `tokenResolver` document and its string-valued `tokenInput` context selection. Its `schemaVersion` remains `0.1.0`; nested contracts retain their own versions. The resolver-backed form can reuse the authoritative foundation source through an explicit URI-to-source-text map supplied to compilation. The reference does not fetch files or URLs. Theme identity, general file packaging, and bundle metadata belong to a later bundle contract. The [illustrative source](../conformance/themes/valid-source.json) is a conformance fixture, not a default palette or product theme. The [authored fixed themes](23-authored-themes.md) are actual light and dark semantic sources built on the foundation scale.

Compilation MUST reject duplicate JSON members at every depth before conversion to an object tree. It MUST validate the source envelope and nested assignments. For a resolver-backed source it MUST compose the selected token sets and modifiers before alias resolution, then validate the complete DTCG token document. It MUST bind every material, color, portable and opaque color fallback, and spatial role. It MUST validate every typography role's token path, declared type, unit, positive constraints, and minimum scale using a baseline user text scale of 1.0. Failures MUST be diagnostic, and no partial compiled theme may be published. Binding errors follow the category and role order in [headless resolution](19-headless-resolution.md).

A compiled theme contains environment-independent resolved tokens and bindings. Resolving it with a validated [environment snapshot](18-environment.md) MUST apply the environment's text scale and role minimum text scales, choose Frost's capability and accessibility fallback, and determine the minimum hit target. For an embedded-token theme, it MUST produce the same semantic snapshot as a headless request carrying identical source fields and that environment. A resolver-backed theme has the same expectation when its composed DTCG token document is supplied to a headless request. Dynamic text scaling may fail if multiplication overflows; a baseline compilation does not promise success for every possible environment. The compiled theme is not a serialized Resina Bundle or render-ready Resina IR. It does not choose a font file, component, state visual, edge, highlight, layout, or renderer technique.

The [source cases](../conformance/themes/source-cases.json) start from the illustrative source and follow the [case schema](../schemas/theme-source-case.schema.json). For a case with `sourceVariant: "resolverBackedInline"`, remove `tokens`, place that same token document as the sole inline source of a `theme` set in `tokenResolver` with DTCG version `2025.10`, set `resolutionOrder` to that set, and add empty `tokenInput` before applying case changes. A `sourceChanges` entry replaces an existing value at an RFC 6901 JSON Pointer path; a `sourceReplace` entry replaces one unique substring of its UTF-8 text to test duplicate members. `schemaValid` records whether strict parsing and the source schema accept the input; `outcome` records whether compilation succeeds. These cases cover structural validation, role binding, typography binding, resolver-backed authoring, and strict parsing without defining a default theme.

The [source root vectors](../conformance/themes/source-vectors.json) supply complete JSON documents for object-root rejection. They cover positional embedded-token and resolver-backed sources with current and unsupported versions, empty arrays, and every primitive JSON kind. These schema-invalid sources are also exercised through valid theme-resolution request envelopes by the external theme checker.

The [theme resolution request](../schemas/theme-resolution-request.schema.json) carries raw theme source text, an explicit external URI-to-source-text map, and a validated environment snapshot. `resina-theme-resolve <path|->` MUST read one UTF-8 request from a file or standard input. It MUST compile the theme before resolving the environment and publish exactly one [headless semantic result](../schemas/headless-result.schema.json) on success. Success exits 0 with no standard error; an invalid request, compilation failure, or resolution failure exits 1 with a diagnostic and no standard output; usage errors exit 2. The Rust command bounds request bytes before parsing. This boundary does not select a theme by identity or publish a Bundle or Resina IR.

The [theme resolution cases](../conformance/themes/resolution-cases.json) use the illustrative source, the environment from the headless request fixture, and its expected semantic result. `resolverBackedInline` applies the transformation above. `foundationResolver` removes the theme's `space` and `type.size` tokens, composes the authored `foundation.json` before the remaining theme tokens, and binds all spatial roles to `space.4` and font-size roles to `type.size.4`; its expected font sizes are 44 px under the fixture's 2.0 text scale. A case may replace one unique substring of theme source text, replace existing values by RFC 6901 pointers in the source or request, omit the external foundation source, or replace existing expected-result values. The [case schema](../schemas/theme-resolution-case.schema.json) constrains these instructions. The [external backend checker](../tools/check_theme_backend.py) validates output shape, complete values, deterministic repetition, diagnostics, and absence of partial output. Passing it establishes conformance only for the covered theme-to-semantic-resolution cases.
