# Color conversion (candidate)

Resina uses the [CSS Color Module Level 4 conversion sequence](https://www.w3.org/TR/2026/CRD-css-color-4-20260930/#color-conversion-code) pinned to the 30 September 2026 draft for conversion among encoded sRGB, XYZ, Oklab, Lab, LCH, and predefined RGB spaces. This contract adopts its color-space transfer functions, RGB-to-XYZ and XYZ-to-RGB matrices, D50-to-D65 adaptation, and Oklab conversion functions. Matrix rows multiply component columns in the order shown there. The reference implementation and the linked conformance vectors must agree with that sequence; no backend-specific color operation defines it.

The forward operation accepts exactly three finite encoded sRGB components in `[0, 1]` and returns Oklab `[L, a, b]`. The reverse operation accepts exactly three finite Oklab components and returns encoded extended-sRGB components. It MUST preserve out-of-gamut values instead of clipping or gamut mapping them. A nonfinite input, out-of-range forward input, or nonfinite result MUST fail explicitly. Alpha is independent of this three-component conversion and is carried separately by the caller. These operations do not choose a palette, pigment, interpolation rule, or output gamut mapping.

For Oklch `[L, C, h]` to Oklab, Resina adopts the pinned CSS `OKLCH_to_OKLab` polar conversion: `[L, C cos(hπ/180), C sin(hπ/180)]`. Input components MUST be finite, with `L` in `[0, 1]`, `C ≥ 0`, and hue in `[0, 360)` degrees, matching DTCG 2025.10 token ranges. Out-of-range input and nonfinite results MUST fail. A zero-chroma hue has no effect on the result. This operation does not interpolate hues or define the missing-component behavior of `none`. The [Oklch vectors](../conformance/color/oklch-conversion-vectors.json) cover axes, zero chroma, and invalid ranges.

For three finite linear-sRGB components in `[0, 1]`, encoded sRGB uses the pinned `gam_sRGB` transfer function on each component `c`: `12.92c` when `c ≤ 0.0031308`, otherwise `1.055c^(1/2.4) − 0.055`. HSL and HWB use the pinned CSS `hslToRgb` and `hwbToRgb` conversions with DTCG input ranges: hue `[0, 360)` degrees and the remaining percentage components `[0, 100]`. For HSL, set `s = S/100`, `l = L/100`, `a = s min(l, 1−l)`, `kₙ = (n + h/30) mod 12`, and `fₙ = l − a max(−1, min(kₙ−3, 9−kₙ, 1))`; output `[f₀, f₈, f₄]`. For HWB, set `w = W/100` and `b = B/100`. When `w+b ≥ 1`, output three copies of `w/(w+b)`; otherwise compute pure hue with HSL `[h, 100, 50]` and output each pure channel multiplied by `(1−w−b)` plus `w`. Nonfinite or out-of-range input and nonfinite results MUST fail. The [direct conversion vectors](../conformance/color/srgb-direct-conversion-vectors.json) cover transfer boundaries, hues, achromatic results, HWB normalization, and invalid ranges.

For `xyz-d65`, apply the pinned CSS `XYZ_to_lin_sRGB` matrix to `[X, Y, Z]` and then `gam_sRGB` to each linear channel. For `xyz-d50`, first apply the pinned `D50_to_D65` Bradford adaptation matrix, then the same sRGB steps. Inputs MUST be finite and each component in `[0, 1]`, as required by the DTCG Color Module 2025.10. The conversion MUST retain extended-sRGB output without clipping; nonfinite results and invalid inputs fail. The [XYZ vectors](../conformance/color/xyz-conversion-vectors.json) fix both whitepoint paths, mixed channels, out-of-gamut output, and input ranges. Alpha remains separate.

For `display-p3`, `a98-rgb`, `prophoto-rgb`, and `rec2020`, the resolver MUST use the pinned CSS sample transfer functions and corresponding linear-RGB-to-XYZ matrices, followed by `XYZ_to_lin_sRGB` and `gam_sRGB`. Display-P3 uses the sRGB decoding function. A98 RGB raises each encoded component to `563/256`; Rec. 2020 raises it to `2.4`. ProPhoto RGB divides a component by `16` at or below `16/512` and otherwise raises it to `1.8`; its XYZ result MUST be adapted from D50 to D65 before sRGB conversion. Each source component MUST be finite and in `[0, 1]` under the DTCG Color Module. The [RGB vectors](../conformance/color/rgb-conversion-vectors.json) fix the transfer curves, matrices, adaptation, extended-gamut output, and input ranges. Conversion does not clamp or map out-of-gamut colors.

For CIE Lab `[L, a, b]`, Resina adopts the pinned CSS `Lab_to_XYZ` conversion with D50 white point `[0.3457/0.3585, 1, (1−0.3457−0.3585)/0.3585]`, `κ = 24389/27`, and `ε = 216/24389`. Set `fᵧ = (L+16)/116`, `fₓ = a/500+fᵧ`, and `f_z = fᵧ−b/200`. The relative X and Z coordinates are `f³` when `f³ > ε`, otherwise `(116f−16)/κ`; relative Y is `fᵧ³` when `L > κε`, otherwise `L/κ`. Multiply by the respective D50 white coordinates, adapt to D65, then convert to encoded extended sRGB. For CIE LCH `[L, C, h]`, first convert to Lab `[L, C cos(hπ/180), C sin(hπ/180)]`. Lab and LCH lightness MUST be finite and in `[0, 100]`; Lab `a` and `b` MUST be finite; LCH chroma MUST be finite and nonnegative and hue MUST be finite and in `[0, 360)` degrees, matching DTCG 2025.10. Nonfinite conversion results MUST fail. Extended-sRGB output MUST remain unclipped. The [Lab/LCH vectors](../conformance/color/lab-conversion-vectors.json) cover D50 neutrals, low-light branches, chromatic conversion, extended output, and invalid ranges. Alpha remains separate.

An extended-sRGB result is not an [sRGB fallback](07-color-fallback.md) unless every channel is in `[0, 1]` under that contract's numerical boundary tolerance. A producer that needs a portable fallback MUST apply a separately specified gamut-mapping rule or use an authored fallback; it MUST NOT silently clamp this conversion result. These are headless color calculations and do not change semantic color assignments.
