# Directional key light (candidate, 0.1.0)

Blueprint §§27–28 require a stable dimensional direction shared by surfaces in a visual context. The [key-light definition](../schemas/key-light.schema.json) supplies one finite, nonzero planar direction toward the light. Its physical axes are `x` toward the right and `y` downward. This direction MUST NOT mirror with layout direction, follow a component role, or change according to a backend name. Logical shape corners must be mapped to physical corners using the actual layout direction before evaluating physical outward normals. The [reference definition](../definitions/key-light.json) points toward the top left; it is an explicit reference choice, not an implicit default.

The [request](../schemas/key-light-request.schema.json) contains the key light, a finite nonnegative side-plane `depth` in logical `px`, and an explicit array of physical outward `normals`. Each normal MUST be finite and nonzero. Normal magnitudes do not encode strength; they are normalized. An empty array is valid and still resolves the straight-edge weights. All fields and version `0.1.0` are required. Missing or unknown fields, unsupported versions, invalid depth, and invalid directions or normals MUST fail without a partial result. A semantic normal validation failure identifies its zero-based array index; source parsing and member/type validation may fail before that stage.

The source request, key-light definition, direction and each normal must be JSON
objects. Positional arrays are invalid at those locations; `normals` itself is
the explicitly ordered array of vector objects.

For any direction `(x, y)`, let `m = max(abs(x), abs(y))`, `a = x/m`, `b = y/m`, and `s = sqrt(a² + b²)`. Its normalized direction is `(a/s, b/s)`. This scaled formula MUST preserve valid subnormal and maximum finite directions without overflowing the length or underflowing it to zero. Implementations MAY use an equivalent algorithm within the conformance tolerance. The reference uses a correctly rounded square root rather than a platform-dependent hypotenuse routine.

Let the unit key direction be `l = (lx, ly)`. The resolved physical side-plane offset is `(-lx × depth, -ly × depth)`, away from the light. Zero depth preserves the light and highlight weights and produces zero offset. This is a portable dimensional convention, not a shadow displacement, physical light position, or a change to surface layout. It does not choose the contour extrusion or paint order.

For a normalized outward normal `n`, the highlight weight is `clamp(dot(n, l), 0, 1)`. This uses the established [normal/direction cosine relation](https://pbr-book.org/3ed-2018/Reflection_Models) as a perceptual directional rule. It is not a physically calibrated reflectance or illumination model. Straight edges use outward normals `(0,−1)`, `(1,0)`, `(0,1)`, and `(−1,0)` for top, right, bottom, and left. Each supplied normal produces one weight in the same array order. Repeated normals are valid and MUST preserve repeated samples.

Curved edges use their actual outward geometric normals; a diagonal endpoint interpolation can give the wrong weights on an ellipse. For an ellipse with positive radii `rx, ry` and radial parameter `(cos θ, sin θ)`, an outward direction is proportional to `(ry × cos θ, rx × sin θ)`, then normalized. Square corners have no unique corner normal; their adjacent straight edges retain their own weights. The sample array allows a backend or conformance tool to evaluate curved edges without a shader or Rust data types. Sampling density and curve realization remain backend responsibilities.

The [result](../schemas/key-light-result.schema.json) records the normalized key direction, physical side offset, four straight-edge weights, and sampled weights. Directions and weights use absolute tolerance `1e-12` without relative tolerance. Side-offset components use absolute tolerance `1e-12` logical `px` or relative tolerance `1e-12`, whichever is larger, because arbitrary finite depth can amplify floating-point rounding. Membership, array length/order, version, and all structural values remain exact. Outputs MUST be finite, with weights in `[0,1]`. [Conformance vectors](../conformance/lighting/key-light-vectors.json) include cardinal and oblique lights, curved and repeated normals, zero depth, extreme finite magnitudes, and diagnostic failures.

`resina-key-light <path|->` reads one UTF-8 request up to 1 MiB. Success exits 0 with one JSON result and no diagnostic; invalid input exits 1 with a diagnostic and no result; usage errors exit 2. Duplicate JSON members are rejected at every depth. The [external checker](../tools/check_key_light_backend.py) validates the public protocol and repeated results without importing Rust.

The operation is valid at Tier 0 and does not require `dynamicLighting`, gradients, masks, or shaders. A backend can realize weighted highlight pigment in ordinary solid bands or sampled curve segments. Applying a weight to [opaque pigment](29-opaque-pigment.md) means scaling the authored highlight lift before compositing white over the opaque body; it does not change body alpha or content color. Bands MUST remain outside content backgrounds unless contrast is re-evaluated for the actual background. The contrast-guarded exterior outline remains separate. Ambient influence, interaction lighting, state response, material anatomy, and complete surface IR still require their own contracts.
