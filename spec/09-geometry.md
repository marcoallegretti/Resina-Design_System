# Surface shape and form (candidate, schema 0.1.0)

The canonical shape intents are `structural`, `soft`, `rounded`, `capsule`, and `organic`. They describe geometry independent of a fixed radius, path primitive, rendering toolkit, or output scale. The five names are distinct semantic choices; consumers MUST NOT infer a shape from material family, component name, or screen category. Major surfaces SHOULD favor continuous curvature, with approximations preserving the intended softness when exact geometry is unavailable.

A surface form supplies one shape and one [semantic elevation](08-elevation.md) under `schemaVersion` `0.1.0`. The [machine-readable schema](../schemas/surface-form.schema.json) requires all three fields and rejects unknown fields or values. Shape and elevation are independent at this generic layer, so all pairs are representable. Component contracts may impose narrower choices when justified by their anatomy or interaction. The [form vectors](../conformance/geometry/surface-form-vectors.json) cover every shape and elevation name and invalid input.

The blueprint's shape hierarchy favors calmer large structural surfaces and softer small interactive controls without requiring universal pill shapes. The [reference foundation](../tokens/foundation.json) includes an authored raw radius scale, covered by [foundation vectors](../conformance/geometry/foundation-radius-vectors.json). Its indices are not shape intents. Exact semantic curvature and visual realization need shape assignments and conformance cases before becoming normative. The surface form is an input to resolution, not a complete Resina IR or layout instruction.

## Bounded corner radii

After a shape's numeric radii and a surface's actual dimensions are known, a headless resolver MUST normalize overlapping corners before rendering. The input has four logical corners (`topStart`, `topEnd`, `bottomEnd`, `bottomStart`), each with nonnegative finite horizontal `x` and vertical `y` radii in the same logical pixel unit as a nonnegative finite surface `width` and `height`. A pair describes a quarter ellipse. Invalid numbers MUST be rejected with a diagnostic. A zero-sized surface is valid and can reduce all radii to zero.

Let the four adjacent sums be `topStart.x + topEnd.x`, `bottomStart.x + bottomEnd.x`, `topStart.y + bottomStart.y`, and `topEnd.y + bottomEnd.y`. For each nonzero sum, divide the corresponding width or height by that sum. The common scale factor is the minimum of these ratios and one. Multiply both axes of all four corners by this factor, including corners that did not individually overlap. A zero sum contributes a factor of one. Implementations MUST avoid overflow when calculating a sum of finite inputs. This follows the [CSS Backgrounds and Borders Level 3 corner overlap rule](https://www.w3.org/TR/css-backgrounds-3/#corner-overlap).

Start and end remain logical until the renderer maps them to physical sides. The [surface-size](../schemas/surface-size.schema.json) and [logical-corner-radii](../schemas/logical-corner-radii.schema.json) schemas constrain the serialized values; the [case schema](../schemas/corner-radius-case.schema.json) identifies valid and invalid vector inputs. This operation does not choose radii for a shape intent or prescribe a path primitive. The [corner-radius vectors](../conformance/geometry/corner-radius-vectors.json) cover unaffected radii, horizontal and vertical overlap, collapsed bounds, and invalid input.

## Tier 0 reference fallback

The [reference fallback assignments](../definitions/tier0-shapes.json) provide one explicit profile for each shape intent under the [assignment schema](../schemas/shape-fallback-assignments.schema.json). The [assignment vectors](../conformance/geometry/shape-fallback-assignment-vectors.json) cover customization and invalid profiles. A `uniform` profile resolves one token path into equal horizontal and vertical radii at all four logical corners. A `corners` profile resolves four token paths into one circular radius per named logical corner. Only `capsule` uses the `capsule` profile, which derives a common radius from half the shorter surface dimension; the Organic fallback uses explicit logical corners. After profile resolution, the headless reference applies the bounded-corner rule above. No profile is inferred from material family or component identity.

Referenced tokens MUST resolve to finite, nonnegative DTCG `dimension` values in `px`, the same logical unit as the surface bounds. Missing tokens, wrong types, invalid values, and unsupported units are diagnostic failures with no geometry result. The reference assignment values and [fallback vectors](../conformance/geometry/shape-fallback-vectors.json) establish reproducible Tier 0 geometry; they do not redefine the five semantic intents as fixed radii. Advanced continuous curvature may refine a silhouette when a later capability contract supports it, but must retain a valid Tier 0 fallback. This fallback is geometry data, not a rendering path or complete Resina IR.
