# Typography roles and resolution (candidate, schema 0.1.0)

Typography roles are `display`, `titleLarge`, `title`, `heading`, `bodyLarge`, `body`, `label`, `caption`, `numeric`, and `code`. A theme supplies a [typography assignment](../schemas/typography-assignments.schema.json) with exactly these roles and `schemaVersion` `0.1.0`. Each role declares an abstract `familyRole` (`sans`, `display`, `monospace`, or `numeric`), paths to resolved DTCG `fontSize`, `fontWeight`, `lineHeight`, and `letterSpacing` tokens, and a `minimumTextScale` of at least 1. Physical font selection belongs to a theme/backend font mapping and MUST NOT be encoded in this semantic assignment. DTCG typography composites remain valid generic token data, but their physical `fontFamily` does not serve as this semantic binding.

Token paths MUST be nonempty. Missing, unknown, or duplicate role members, unknown properties or family roles, and unsupported versions are errors. Duplicate JSON members MUST be rejected before conversion to an object tree. A role's `fontSize` and `letterSpacing` tokens MUST be valid DTCG `dimension` values with unit `px`; `fontSize` MUST be positive and `letterSpacing` MAY be negative. The `fontWeight` token MUST be a valid DTCG `fontWeight` value and resolves to its numeric OpenType weight; named aliases use the DTCG values. `lineHeight` MUST be a positive DTCG `number` multiplier. Missing, wrong-type, invalid, or nonportable token values are errors. Resolution reports all role-field errors in the role order above and field order `fontSize`, `fontWeight`, `lineHeight`, `letterSpacing`, without publishing a partial mapping.

The environment supplies a positive `textScale`. Each role's effective scale is `max(textScale, minimumTextScale)`. The resolver multiplies `fontSize` and `letterSpacing` by that scale, preserves the `px` unit and line-height multiplier, and rejects any nonfinite result. It MUST NOT reduce text when the user requests a larger scale. Font-family role and numeric font weight remain unchanged. The returned metrics are headless semantic typography, not a physical font file or a renderer text object. Component contracts must separately provide wrapping, growth, and reflow; a larger metric alone cannot prove that text remains available at 200%.

The [DTCG Format Module 2025.10](https://www.designtokens.org/TR/2025.10/format/) allows `px` and `rem` dimensions and defines `rem` relative to the system default font size. The current [environment snapshot](18-environment.md) has no such root-font-size field. Generic DTCG tokens MAY use `rem`, but assigning them to Resina typography metrics would make headless scaling ambiguous, so this candidate contract requires `px`. A future version may admit `rem` after specifying the font context and preventing double application of user scaling. The [assignment vectors](../conformance/typography/assignment-vectors.json), [resolution vectors](../conformance/typography/resolution-vectors.json), and [font-weight alias vectors](../conformance/typography/font-weight-alias-vectors.json) define valid and rejected cases.

The [foundation token source](../tokens/foundation.json) defines the candidate raw type-size scale `type.size.0` through `type.size.7` as 12, 14, 16, 18, 22, 28, 36, and 48 logical `px`. The [foundation vectors](../conformance/typography/foundation-vectors.json) fix their resolved DTCG values. Representative display, title, body, label, and caption samples were inspected at 100% and 200% text scale in a fixed-width layout; the larger samples grew and wrapped without clipping. This calibration does not select a font, assign a size to every semantic role, establish component reflow, or make a physical-pixel promise. A theme chooses role-to-token paths explicitly, and its backend font mapping needs separate evidence.
