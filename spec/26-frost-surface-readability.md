# Frost surface color readability (candidate, 0.1.0)

The request MUST be a JSON object. Positional arrays and other non-object roots are invalid.

The [request](../schemas/frost-surface-readability-request.schema.json) joins one complete [surface scenario](21-surface-scenarios.md), a semantic `foregroundRole`, the actual opaque `postTreatmentBackdrop` below the bound surface, the actual opaque `adjacentColor` at one edge location, and separate content and edge contrast thresholds. Both thresholds are finite numbers from 1 through 21. The request is strict JSON: duplicate members, unknown members, unsupported versions, invalid colors, and nonfinite numbers are errors. The operation is headless and has no renderer or component identity.

The resolver MUST complete the scenario once and use its single semantic snapshot for the surface, foreground, and both outline roles. The material family MUST be Frost. The bound state set MUST contain only `rest`, `focused`, or both, and the bound surface's final treatment MUST be `none`. Focus MUST preserve the same body readability result and the complete supplied state set in canonical order, without inferring `rest`. A focused consumer MUST separately resolve and display the [navigation indicator](27-focus-indicator.md) for the same intent; this body result does not contain it. Every other state MUST fail until its body appearance has a separate resolution contract. This operation does not invent state visuals or the effect of an active optical treatment on surface pigment. Ancestor treatments MAY be present because the caller supplies the known post-treatment backdrop. The `foregroundRole` MUST use its resolved portable sRGB color, which MUST be opaque. Its authored opaque fallback may be a distinct Tier 0 tone and MUST NOT silently replace the active foreground here. The backdrop and adjacent colors MUST be opaque sRGB. The resolver MUST NOT silently substitute a default role or color.

The resolver first applies [Frost legibility](24-frost-legibility.md) to the bound representation, portable body, authored opaque body, resolved foreground, known backdrop, and `minimumContentContrast`. It then applies [edge contrast](25-edge-contrast.md) to the same snapshot's `outline` and `outline.strong` opaque fallbacks, the known adjacent color, and `minimumEdgeContrast`. A failure at any step publishes no result. The [result](../schemas/frost-surface-readability-result.schema.json) retains the preliminary binding, selected foreground role and color, final Frost legibility decision, and selected edge color. If legibility falls back, its representation and body supersede the preliminary Frost representation and body in the binding. A consumer MUST use the final legibility decision for these color channels.

The [cases](../conformance/surfaces/frost-readability-cases.json) test translucent retention, opaque content fallback, stronger edge selection, unreadable content, indistinct edges, and rejected states, treatment, material, and input. The Rust reference also exposes a typed operation that accepts a surface intent and one resolved semantic snapshot; it binds that intent internally so a caller cannot pair a bound surface with an unrelated snapshot. `resina-frost-surface-readability <path|->` reads one UTF-8 request from a file or standard input, bounded to 1 MiB. Success exits 0 with one strict JSON result and no diagnostic; resolution failure exits 1 with no result and a diagnostic; usage errors exit 2. The [external checker](../tools/check_frost_surface_readability_backend.py) verifies the public command protocol and deterministic output.

This local result evaluates the specified base pigment and role colors at one known backdrop and edge adjacency. It does not resolve edge geometry, highlight, depth, variable backdrop regions, text size, state-dependent colors, treatment rendering, or complete accessibility conformance. It is not render-ready Resina IR. A surface whose foreground, body, or edge changes through state or treatment requires the effective colors to be resolved and checked for those conditions before painting.

Failure diagnostics follow the [public backend diagnostic policy](32-headless-conformance.md#failure-diagnostics). Negative public cases use `failure: true`; diagnostic wording is not a conformance requirement.
